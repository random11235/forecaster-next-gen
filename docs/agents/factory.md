# The factory

The factory is [`.github/workflows/factory.yml`](../../.github/workflows/factory.yml): labelling an issue `ready-for-agent` builds it with an agent on GitHub's runners. Cycle time and the rest of the Ticket lifecycle are in [`issue-tracker.md`](issue-tracker.md#ticket-lifecycle); this is what the workflow does with a ticket and a spec, and how to recover one it parked.

Under the factory (`.github/workflows/factory.yml`), labelling an open ticket outside any spec `ready-for-agent` builds it on GitHub's runners, unless it already has an open PR. The workflow does every write: it swaps `ready-for-agent` for `in-progress` and comments the run link, then, once `npm run check` passes on the agent's commits, opens a PR to `main` that closes it, from `agent/<n>-<run id>`, with the body the agent wrote with `/pr`. A run that fails parks the ticket: it removes `in-progress` (and `ready-for-agent`, if still there), adds `parked`, and comments why; the agent's transcript and Sandcastle's log are in the run's `factory-logs` artifact. Label it `ready-for-agent` again to rebuild it on a new branch. Labelling a spec `ready-for-agent` builds its next ticket instead: the first of its sub-issues, in order, that is open, not merged into `spec/<n>`, not `parked` or `ready-for-human`, and has no open blocker other than a ticket already merged (`factory/factoryFrontier.ts`). It is built on `spec/<n>`, made from `main` if it isn't there yet; the ticket gets `in-progress`, and once `npm run check` passes on the merged tree and `spec/<n>` is pushed, it gets the factory's comment `merged into spec/<n>`, and stays open. The spec then gets the ticket's entry in its **decision log**: a comment opening with the hidden mark `<!-- forecaster-decision -->`, by `github-actions[bot]`, holding the ticket's number and title and the PR body its agent wrote, but its Evidence, cut to fit a comment (`factory/factoryDecisionLog.ts`). The entries, oldest first, are what each ticket decided, and which reading it took, for the spec's later tickets to allow for: each later ticket's prompt gives them in the `<spec>` block, after the spec's body, leaving out the oldest to fit the prompt and saying how many. An entry by anyone else, the owner too, or without the mark, is left out, and so are the spec's other comments. An entry that fails to post only warns: the ticket has merged. The log is a record kept with the spec, as its comments, not a file: once the spec closes nothing reads it, though the owner still can in GitHub. Only that comment, opening with the factory's mark, counts as merged into `spec/<n>`: by the factory, which writes as `github-actions[bot]` with its job's `GITHUB_TOKEN`, or by the owner, a member or a collaborator by hand. An `/implement-spec` `merged` comment doesn't, as its merge is into its own integration branch. The spec loses `ready-for-agent` and never gets `in-progress`. A `ready-for-human` spec ticket is never built: build it locally, merge it into `spec/<n>`, then comment `merged into spec/<n>` by hand, opening with the mark; tickets it blocks wait, and so does the spec's PR. A spec ticket whose build fails is parked and `spec/<n>` left unchanged: take `parked` off and label the spec again to retry. One whose commits change `.github/` is parked and not pushed, and a retry would be refused again: build it locally, merge it into `spec/<n>`, then comment `merged into spec/<n>` by hand, opening with the mark, and take `parked` off. One whose commits reached `spec/<n>` but got no merged comment, because the comment failed or the push's step didn't finish, is parked too: comment `merged into spec/<n>` by hand, opening with the mark, and take `parked` off. After a push that failed, or wasn't known to finish, park reads `spec/<n>` and reports whether the push landed or the branch is unchanged. Only when `spec/<n>` moved to some other commit, or reading it failed, can't the factory tell whether it has the ticket's commits, and the park comment says so: if it has them, comment merged by hand; if not, retry. A spec with no ticket to build, or a run whose check of the labelled issue fails, is told why in a comment, and parks nothing: a ticket outside any spec too, whose failed check parked it before specs were built. A ticket whose commits would leave `.sandcastle`, `node_modules`, or a `.claude` or `.claude/skills` that isn't a directory in its branch, `spec/<n>` or `agent/<n>-<run id>`, which the factory won't build on, is parked and not pushed; a branch already holding one parks the ticket before the agent runs, until the owner fixes it. A spec's earlier agents' code on `spec/<n>` runs only in the sandbox: the runner's own code, dependencies and hooks are `main`'s. A spec's ticket labelled on its own isn't built. Every factory comment but a decision-log entry carries a hidden `<!-- forecaster-factory -->` mark, which keeps it out of the next build's prompt. The agent runs upstream's `/implement`, on a prompt (`factory/factoryTicket.ts`) that opens with `/implement <n>` and then gives the factory's rules for an unattended run, before the ticket: make no GitHub calls, build only the ticket when a spec follows it, choose the reading that changes least and say so in the commit message, give `code-review` the ticket, commit everything, meet whatever `npm run check` requires (the repo's rules, through `AGENTS.md`, say what), and end with a `<pr-body>` written with `/pr`. The rules name no file or rule of this repo's, so `/implement` stays upstream's copy, installed from `skills-lock.json` and untracked.

## A spec's chain

Once a spec's ticket merges into `spec/<n>`, the factory starts its own next run on the spec: `publish` dispatches `factory.yml` (`workflow_dispatch`, with the spec's number and the hop count plus one) with its job's `GITHUB_TOKEN` and `actions: write`, as a dispatch is the one event that token may start a workflow with. The run its label started is hop 0. The next run is `main`'s, waits in the spec's concurrency group for the one that started it to end, and picks the spec's next ticket as a label's run does, so a ticket blocked by one just merged is built on a `spec/<n>` holding its code. Each run comments on the spec which ticket it builds. The chain stops, and the spec gets a factory comment saying why, when no ticket can be built (each one left is parked, for a human or blocked), when every ticket is in (that run opens the spec's PR, below), when a ticket is parked (a failed build or check, or a push to `spec/<n>` refused because the branch moved, which leaves it unchanged), when starting the next run fails, or at the hop cap, the spec's number of sub-issues: a run at that hop builds nothing (`factory/factoryFrontier.ts`), so one label's chain builds at most one ticket for each, and a ticket picked again and again can't be rebuilt past it. Label the spec `ready-for-agent` again to start a new chain at hop 0. A dispatch by `github-actions[bot]` is taken as the factory's, as only this repo's own workflows hold a `GITHUB_TOKEN` that can dispatch; anyone else's, from the Actions tab, needs write access, as a label does, and runs only on a spec.

## A spec's PR

Once every ticket of a spec is closed or merged into `spec/<n>`, the run that finds it so, chained or labelled, opens the spec's one PR, from `spec/<n>` to `main`, in its `propose` job, with `FACTORY_TOKEN`, so CI runs on it. Its title is the spec's (or `Spec #<n>`, if someone outside the repo opened it), and its body (`factory/factorySpecPullRequest.ts`) links the spec and lists every ticket in a table, with its status, then says the spec's decision log is in its comments, then Evidence and Merge Danger. It has no closing keyword: GitHub's stop at 10 issues. It doesn't give the log itself, whose entries are agents' PR bodies and could hold closing keywords. A run that finds an open PR from `spec/<n>` already opens no second, and one that finds no `spec/<n>`, or one with no commits `main` lacks, so nothing to merge, opens none; each way, and when opening it fails, the spec is told in a comment. The owner reviews and merges it: the factory never merges.

When a PR from this repo's `spec/<n>` merges into `main`, the `close` job, on `pull_request_target`, closes the spec and every one of its sub-issues, read page by page, so past 10 and past 100, takes `ready-for-agent` and `in-progress` off each, and deletes `spec/<n>`, commenting on the spec as it starts (`factory/factorySpecMerged.ts`). A closed ticket only has the labels taken off. An issue with no sub-issues closes nothing, and neither does a fork's PR, a PR into another branch, or one closed unmerged. The job checks out only `main` and runs none of the PR's code, holding `issues: write`, `contents: write` for the branch and `actions: write` for the board sync, pinned in `factory/test/workflowPermissions.test.ts`. Merging a ticket into `spec/<n>` is a push, not a PR, so closes nothing. A close or label removal that fails fails the job, and the spec gets a comment naming the issues to see to by hand.

## Asking `@claude`

The owner or a collaborator can ask about an issue or a PR in a comment that mentions `@claude`, and the factory answers in one reply on it, carrying the mark. A mention from anyone else, a comment without one, and the factory's own comments start nothing (`factory/factoryQuestion.ts`). A question builds nothing: its `ask` job runs Claude Code in the sandbox, on a checkout of `main` and what a step fetched beforehand into its prompt: the issue (its title and body if a collaborator opened it, labels, the owner's, collaborators' and factory's comments, but not the factory's earlier replies to questions), its linked PRs with their checks, and `main`'s latest 30 commits. Asked about a spec, it gets the spec's decision log too, in place of the entries among its comments; asked about a spec's ticket, the spec's title and body and its decision log, on the same terms as a build's prompt. Its only tools are Read, Grep and Glob, with no shell, and the sandbox holds no GitHub token, only the OAuth one (`readOnlyAgent()` in `factory/factorySandcastle.ts`). It can't edit, push, comment or label. Whether a comment asks is decided before the job installs anything, so `factory/factoryAsked.ts` and what it imports may import no package, which `factory/test/factoryAsked.test.ts` checks. The issue's text is data to it, never instructions. The `reply` job, holding `issues: write`, posts the answer, or why there is none; the agent's transcript is in the run's `factory-logs` artifact. Building stays with the `ready-for-agent` label.

## The module

The factory is one module, [`factory/`](../../factory), apart from the app. Its scripts are at its root, each entry script a file a workflow step runs with `node`; their tests are in `factory/test/`; its composite actions, `sandbox` and `ticket-branch`, are in `factory/actions/`, and the plan check for triage is `factory/triagePlan.ts`. Its workflows stay in `.github/workflows/` (`factory.yml`, `factory-relay.yml` and `factory-smoke.yml`), where GitHub reads them. `npm run lint:boundaries` fails on an import from the factory into the app (`src/`, `scripts/` or `test/`) or from the app into the factory; the factory may import Sandcastle and Node's built-ins. Its jobs install Node and run the install command themselves, never through CI's `.github/actions/setup`, so changing CI can't change the factory, which `factory/test/factorySetup.test.ts` pins.

## The config

Every repo-specific value the factory uses has one source: `factory.yml`'s top-level `env:`, each with its default. These are the trigger, parked and in-progress labels; the mark and the brief mark; the install and check commands; the Node version; the build's model, budget and time limits; the skills a build needs; and, for a question, the mention, model, budget, idle timeout, job timeout and how many commits its prompt lists. Steps read them as `$NAME` or `${{ env.NAME }}`. Scripts read them only through [`factory/factoryConfig.ts`](../../factory/factoryConfig.ts), which fails on a value left unset, naming it, and imports nothing, so `factoryAsked.ts` still imports no package. A job's `if` and `timeout-minutes`, and the concurrency group, can't read `env`, so they repeat the value with a comment naming it, and `factorySetup.test.ts` fails if they differ, as it does for the mention `factory-relay.yml` filters on. Before the agent runs, the build's install step runs `factory/factorySkills.ts`, which fails naming each required skill the runner's checkout lacks.

## Sandcastle

The factory runs its agent in [Sandcastle](../research/sandcastle-factory.md), pinned at exactly 0.14.0. Only [`factory/factorySandcastle.ts`](../../factory/factorySandcastle.ts) imports it: the build, question and smoke scripts build their agent, run it in the sandbox and read what it threw through that adapter, whose header lists what it relies on that Sandcastle doesn't promise to keep. To bump Sandcastle, change that module and its test, then dispatch the smoke test (`.github/workflows/factory-smoke.yml`) by hand.
