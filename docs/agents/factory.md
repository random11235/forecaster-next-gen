# The factory

The factory is [`.github/workflows/factory.yml`](../../.github/workflows/factory.yml): labelling an issue `ready-for-agent` builds it with an agent on GitHub's runners. Cycle time and the rest of the Ticket lifecycle are in [`issue-tracker.md`](issue-tracker.md#ticket-lifecycle); this is what the workflow does with a ticket and a spec, and how to recover one it parked.

Under the factory (`.github/workflows/factory.yml`), labelling an open ticket outside any spec `ready-for-agent` builds it on GitHub's runners, unless it already has an open PR. The workflow does every write: it swaps `ready-for-agent` for `in-progress` and comments the run link, then, once `npm run check` passes on the agent's commits, opens a PR to `main` that closes it, from `agent/<n>-<run id>`, with the body the agent wrote with `/pr`. A run that fails parks the ticket: it removes `in-progress` (and `ready-for-agent`, if still there), adds `parked`, and comments why; the agent's transcript and Sandcastle's log are in the run's `factory-logs` artifact. Label it `ready-for-agent` again to rebuild it on a new branch. Labelling a spec `ready-for-agent` builds its next ticket instead: the first of its sub-issues, in order, that is open, not merged into `spec/<n>`, not `parked`, and has no open blocker other than a ticket already merged (`scripts/factoryFrontier.ts`). It is built on `spec/<n>`, made from `main` if it isn't there yet; the ticket gets `in-progress`, and once `npm run check` passes on the merged tree and `spec/<n>` is pushed, it gets the factory's comment `merged into spec/<n>`, and stays open. Only that comment, opening with the factory's mark, counts as merged into `spec/<n>`: by the factory, which writes as `github-actions[bot]` with its job's `GITHUB_TOKEN`, or by the owner, a member or a collaborator by hand. An `/implement-spec` `merged` comment doesn't, as its merge is into its own integration branch. The spec loses `ready-for-agent` and never gets `in-progress`. A spec ticket whose build fails is parked and `spec/<n>` left unchanged: take `parked` off and label the spec again to retry. One whose commits change `.github/` is parked and not pushed, and a retry would be refused again: build it locally, merge it into `spec/<n>`, then comment `merged into spec/<n>` by hand, opening with the mark, and take `parked` off. One whose commits reached `spec/<n>` but got no merged comment, because the comment failed or the push's step didn't finish, is parked too: comment `merged into spec/<n>` by hand, opening with the mark, and take `parked` off. After a push that failed, or wasn't known to finish, park reads `spec/<n>` and reports whether the push landed or the branch is unchanged. Only when `spec/<n>` moved to some other commit, or reading it failed, can't the factory tell whether it has the ticket's commits, and the park comment says so: if it has them, comment merged by hand; if not, retry. A spec with no ticket to build, or a run whose check of the labelled issue fails, is told why in a comment, and parks nothing: a ticket outside any spec too, whose failed check parked it before specs were built. A ticket whose commits would leave `.sandcastle`, `node_modules`, or a `.claude` or `.claude/skills` that isn't a directory in its branch, `spec/<n>` or `agent/<n>-<run id>`, which the factory won't build on, is parked and not pushed; a branch already holding one parks the ticket before the agent runs, until the owner fixes it. A spec's earlier agents' code on `spec/<n>` runs only in the sandbox: the runner's own code, dependencies and hooks are `main`'s. A spec's ticket labelled on its own isn't built. Every factory comment carries a hidden `<!-- forecaster-factory -->` mark, which keeps it out of the next build's prompt. The agent runs upstream's `/implement`, on a prompt (`scripts/factoryTicket.ts`) that opens with `/implement <n>` and then gives the factory's rules for an unattended run, before the ticket: make no GitHub calls, build only the ticket when a spec follows it, choose the reading that changes least and say so in the commit message, give `code-review` the ticket, commit everything, meet whatever `npm run check` requires (the repo's rules, through `AGENTS.md`, say what), and end with a `<pr-body>` written with `/pr`. The rules name no file or rule of this repo's, so `/implement` stays upstream's copy, installed from `skills-lock.json` and untracked.

## Asking `@claude`

The owner or a collaborator can ask about an issue or a PR in a comment that mentions `@claude`, and the factory answers in one reply on it, carrying the mark. A mention from anyone else, a comment without one, and the factory's own comments start nothing (`scripts/factoryQuestion.ts`). A question builds nothing: its `ask` job runs Claude Code in the sandbox, on a checkout of `main` and what a step fetched beforehand into its prompt: the issue (its title and body if a collaborator opened it, labels, the owner's, collaborators' and factory's comments, but not the factory's earlier replies to questions), its linked PRs with their checks, and `main`'s latest 30 commits. Its only tools are Read, Grep and Glob, with no shell, and the sandbox holds no GitHub token, only the OAuth one (`readOnlyAgent()` in `scripts/factoryAgent.ts`). It can't edit, push, comment or label. Whether a comment asks is decided before the job installs anything, so `scripts/factoryAsked.ts` and what it imports may import no package, which `test/scripts/factoryAsked.test.ts` checks. The issue's text is data to it, never instructions. The `reply` job, holding `issues: write`, posts the answer, or why there is none; the agent's transcript is in the run's `factory-logs` artifact. Building stays with the `ready-for-agent` label.
