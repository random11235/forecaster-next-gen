# Architecture: Storage tests

Part of the test seams; see [`architecture-test-seams.md`](architecture-test-seams.md), whose index is [`architecture.md`](architecture.md).

`test/storage/` holds the Storage contract, one suite run against both the SQLite file and the web build's browser storage, and the schema migration tests. The team's connection, the last read of each query, the milestone's picks and query, and its setup: where it stands (`setups`: open or closed, how, and what the steps did to the connection), its draft (`setup_drafts` with its reads, their tickets and its picks' failures in rows of their own) and why its last reads failed (`read_failures`, by what failed: whole, a query's, or a pick's) (`ConnectionStorage`, `SavedReadStorage`, `MilestoneQueryStorage` and `SetupStorage`, part of `openSqliteStorage`'s `SqliteStorage`) are kept only by the SQLite file, so their cases run against SQLite alone: the browser build has no connectors. The team's queries and reads come in two targets (`TeamQueryStorage.teamQueries`): `current`, the setup draft over what's saved while setup is open, otherwise what's saved, which the setup steps read and save; and `saved`, what's saved only, which the forecast reads. Applying the draft ("Use these", `TeamQueryStorage.applySetupDraft`), discarding it (Cancel, `discardSetupDraft`), and saving its sources and picks' failures (`saveDraftSources`, `saveDraftPickFailures`) are storage operations. The setup draft over what's saved is plain TypeScript in `src/storage/lib/setupDraft.ts`, behind `sqliteStorage.ts`, tested only through the contract: its cases cover each target with setup open and closed, applying the draft and discarding it. Stored JSON is read only through `parseStored` in `src/storage/lib/storedJson.ts`, which checks each value's shape (`test/storedJsonRules.test.ts` fails on any use of the `JSON` global but `JSON.stringify` anywhere else in `src/storage/`, comments and strings aside); the contract's cases for stored data storage can't read, text that isn't JSON or a blob of a shape it doesn't know (`storageContract.storedShape.test.ts`), run against both storages, each seeded its own way: each refuses it, naming its column or browser storage's key, and keeps it through the Storage contract's saves: browser storage, one record, refuses every save, and the SQLite file takes them, but its save of the milestone inputs replaces a refused value in that record whole. The SQLite-only tables' own saves (the queries', the setup draft's) aren't tried over a refused value. Neither keeps a field it doesn't know in data it can read: saving that record drops it. Browser storage with nothing stored starts empty. `webApp.test.ts` checks that the web build fails each screen on it as the server fails a request, a 500 giving the error. The migration tests are not a forecasting seam either: they write a data file as an earlier release left it, open it through `openSqliteStorage`, and check what reads back, through storage or through Seam B's views. A branch into main that changes the schema appends at most one step to `MIGRATIONS` in `src/storage/sqliteStorage.ts`, never editing a released one, and adds a test there that opens a file from the version before, naming its step in a `describe('step N: …')`: `test/storage/migrationCoverage.test.ts` fails, naming the step, on any step no `migrations.*.test.ts` names. Tickets on an integration branch extend that branch's one unreleased step rather than appending their own. `npm run check:migrations` (part of `npm run check`, so of the pre-push hook and CI) checks both rules against main. The values of every union that reaches storage are frozen by a snapshot, `test/storage/storedValues.snapshot`. `storedUnions.ts` lists the unions, each with the columns that store it, bound to their types by the typecheck, which also fails on a union a storage's `save…` method takes that isn't listed. A union the SQLite file writes that no `save…` method takes (`read_failures.of`) is typed in `storedUnions.ts`'s `SqliteEncodings` instead, and the typecheck can't tie it to the literals the file writes: `storageContract.storedValues.test.ts` checks the file writes exactly its listed values, and reads back every listed value of each union it reads by a list of its own (how setup was closed, what an opening did to the connection, a read's failure, a drafted source). `storedValues.test.ts` fails on a listed union the snapshot doesn't hold as listed, and on a value in the snapshot at the merge-base with released main (`MAIN_REF`, origin/main, as the migration check; never `CHECK_BASE`, since only released values can be in saved data) that a column no longer stores, unless a migration step on the branch maps it in that column (its statements on the column name it, quoted, more often than the base's do) and, for a union the web build's storage keeps, `webStorage.ts` still names it in its code, to map it as it reads. A union only renamed, its values stored where they were, needs no migration. Two limits are known: the web build's storage has no columns, and its code naming a value at all counts as mapping it, for every union that has it, even where it names the value for another reason; and a statement is on a column when it names the table and the column anywhere, in a subquery too.
