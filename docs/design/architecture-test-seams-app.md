# Architecture: App tests

Part of the test seams; see [`architecture-test-seams.md`](architecture-test-seams.md), whose index is [`architecture.md`](architecture.md).

`test/app/` holds the launch smoke test. It is not a forecasting seam: it builds the app, runs the built `npm start` entry point (`dist/app/main.js`) with `FORECASTER_NO_BROWSER=1` so no browser opens and a temporary `FORECASTER_DATA_FILE`, and checks that the Milestone forecast screen is served in its empty state, with no sample data. It runs it again in demo mode (`FORECASTER_DEMO=1`), on the canned connector built from the synthetic fixture, so no token is needed, and checks the screen is served. It also checks that a bad `PORT` is refused. `test/app/launch.test.ts` starts the server in-process, on port 0, and checks that it refuses a request whose `Host`, or a POST whose `Origin`, isn't its own, with no route run, sending a foreign `Host` through `node:http` because `fetch` sets its own.

The web build is tested the same way, with no seam of its own: `webApp.test.ts` asks its app for screens as its page does, and the web build smoke test runs `npm run build:web` and checks the one page it writes opens on the empty state with its script inline. The smoke test also runs that script, as bundled, in Node on a stub of the browser parts it opens with, and posts a milestone and pace through the `fetch` it answers for the Inputs screen's saves, so what the bundling breaks in the app fails a test (#280). Its page script's (`webMain.ts`) wiring of links and forms in a real browser is checked by the browser check (`npm run check:browser`, a CI job of its own), which drives the local app and the web build in Chrome from empty to a forecast, and by the ticket's demo, not by tests.

The Inputs screen's browser scripts are tested in `test/app/` too, in [happy-dom](https://github.com/capricorn86/happy-dom), so no browser is installed, locally or in CI (#275). `test/app/browserPage.ts` opens a page of `appOnTracker`'s running app at its URL, with JavaScript on in that helper alone, as it opens only the app's own pages, and the `/live` reload script's `EventSource` stubbed so tests end. The page's scripts run as the browser runs them, and their `fetch` reaches the real server, the canned connector and the storage in memory, with nothing faked. A test changes a field and fires its event, waits for the page to settle (`settled`, which waits out each request and timer, the candidates' debounce among them), then checks the page and what storage now holds; to make answers arrive out of order, it holds one back (`holdAnswer`), and waits on what the page shows meanwhile (`until`, which fails, saying what it waited for, if the page doesn't show it within a limit far longer than any answer takes). `settled` fails at once while an answer is held, rather than wait on it, and fails on each error the page's scripts left uncaught, as happy-dom reports it on the window: thrown as a script ran, in a listener or in a timer; so does opening the page. An error a script catches is its own to show, and a promise rejection left unhandled fails the run through Vitest. `pagesOnTracker.ts` opens each test's page and closes it, and its app, after; `browserPage.test.ts` tests that the page fails these tests fast and says why. `inputsScript.test.ts` tests the Inputs screen's script (`INPUTS_SCRIPT`): a change saved and noted, the header swapped in with the sections, a refusal swapping in its section alone, a date field saved on leaving it, saves in order, the focus and selection kept, and what is typed while a save is answered, the Connect step left alone, an unchanged form not posted, the server not answering, and a chip's dot and Follow. `candidatesScript.test.ts` tests the Comparable work step's candidates script: a link opening a candidate in place, narrowing to a few (`FEW_CANDIDATES` or fewer) opening those once the typing pauses (`NARROWED_DEBOUNCE_MS`) and to more opening none, both read, by the script and the test alike, from the candidates block the page carries them on, typing that goes on opening nothing, an emptied find box opening nothing, and a stale answer ignored. `setupStepScripts.test.ts` tests the Milestone step's find box (`queryStepScript`): the lists narrowed as the EM types, read from what the page's styles display, so a style showing what the script hid fails it, nothing found said, and a kind past what was listed asked of the tracker once the typing pauses; and that a source chosen at Check (`CHECK_SCRIPT`) posts at once. happy-dom submits a form as multipart, which the server doesn't read, so what that post saves stays tested over HTTP.

Each screen's rendering is tested as a component, in `test/app/components/`, with no server started (#236). A component test owns a view rendered: it calls a render function (`renderInputsScreen`, `renderMilestoneForecastScreen`, `renderHowItWorksScreen`, `queryStepSection`, `candidatesHtml`, setup's `setupStepHtml`, `checkStepHtml`, `setupSummaryHtml` and `setupSkippedHtml`, `connectSection`, and `renderPaceTrend`) with a view, built by hand or taken whole from Seam B (`forecastingForTest`), and checks what the page offers the EM: each region, heading, field, button and link by its role and accessible name, the visible text, and where each form posts. It covers the states a view can be in: empty, refused with why, warned, and each source of tickets remaining and pace, with the chip on a typed value the tracker reads differently. What the view says, and when, is Seam B's, so a component test checks no forecast: a date or count it reads is one the view it renders gave. `test/app/dom.ts` parses the HTML in one happy-dom window with JavaScript off, and queries it by role and name as a screen reader would (`byRole`, `allByRole`, `hasRole`, `accessibleName`), by visible text (`text`, block elements kept apart), and by selector where a role says too little (`one`, `around`); a closed `<details>` hides all but its summary. The render functions' files are listed for `app` in `TEST_SEAMS`, as the component layer's entry points.
