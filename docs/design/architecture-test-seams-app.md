# Architecture: App tests

Part of the test seams; see [`architecture-test-seams.md`](architecture-test-seams.md), whose index is [`architecture.md`](architecture.md).

`test/app/` holds the launch smoke test. It is not a forecasting seam: it builds the app, runs the built `npm start` entry point (`dist/app/main.js`) with `FORECASTER_NO_BROWSER=1` so no browser opens and a temporary `FORECASTER_DATA_FILE`, and checks that the Milestone forecast screen is served in its empty state, with no sample data. It runs it again in demo mode (`FORECASTER_DEMO=1`), on the canned connector built from the synthetic fixture, so no token is needed, and checks the screen is served. It also checks that a bad `PORT` is refused. `test/app/launch.test.ts` starts the server in-process, on port 0, and checks that it refuses a request whose `Host`, or a POST whose `Origin`, isn't its own, with no route run, sending a foreign `Host` through `node:http` because `fetch` sets its own.

The web build is tested the same way, with no seam of its own: `webApp.test.ts` asks its app for screens as its page does, and the web build smoke test runs `npm run build:web` and checks the one page it writes opens on the empty state with its script inline. The smoke test also runs that script, as bundled, in Node on a stub of the browser parts it opens with, and posts a milestone and pace through the `fetch` it answers for the Inputs screen's saves, so what the bundling breaks in the app fails a test (#280). Its page script (`webMain.ts`) is tested in happy-dom by `webMain.test.ts` (#237): `test/app/webPage.ts` imports it in Vitest's own process, on a happy-dom window put in place of the browser's globals, so the coverage counts it, its storage, history and own `fetch` arranged per test; the globals it stubs are listed on `webPages`. The tests check the screen the URL's fragment opens on, a link or form answered by the app and the path kept in the fragment, at the part it names, the back button, the Inputs screen's saves answered through its `fetch` and found again on reopening, a save asking through `fetch` to be answered in place (the `SAVE_IN_PLACE` header) answered with the Inputs screen and one not asking with the screen it goes to, what it leaves to the browser (a link clicked with a key held, a link or form to another site, a fetch past the app's paths), and the page still working with storage blocked, a history entry refused, or storage it can't read. How it looks in a real browser is checked by the browser check (`npm run check:browser`, a CI job of its own), which drives the local app and the web build in Chrome from empty to a forecast, and by the ticket's demo.

The Inputs screen's browser scripts are tested in `test/app/` too, in [happy-dom](https://github.com/capricorn86/happy-dom), so no browser is installed, locally or in CI (#275). `test/app/browserPage.ts` opens a page of the app at an address nothing serves, with JavaScript on in that helper alone, as it opens only the app's own pages. Each request the page sends, its scripts' `fetch` and the forms it submits, is answered in-process (#237) by `appInProcess.ts`: the server build's routes, on the canned connector and the storage in memory (`cannedTrackerApp.ts`, which `appOnTracker.ts` serves the same parts from, and `inputsSection.ts` cuts the Inputs screen to a section for either), with no server started and nothing else faked, a redirect followed as a browser follows one, and a request it can't answer once stopped (`stopApp`) failing as one to a stopped server does: a script's `fetch` rejects, a form posted opens a stand-in for the browser's own page saying it can't reach the site (`CANT_BE_REACHED`), as happy-dom shows none, and any other navigation fails, opening the page among them. What happy-dom's public interface can't do or doesn't say, a request failed, a page at the address its answer came from, and a navigation's request told from a script's `fetch`, is done in one adapter, `happyDomAnswers.ts`, which `browserPage.test.ts` pins. Each request the page sent is kept with the routes' own reply to it (`requests`), so a test reads what the routes answered, not only what the page shows of it. The page's scripts run as the browser runs them. A test changes a field and fires its event, waits for the page to settle (`settled`, which waits out each request and timer, the candidates' debounce among them), then checks the page and what storage now holds; to make answers arrive out of order, it holds one back (`holdAnswer`), and waits on what the page shows meanwhile (`until`, which fails, saying what it waited for, if the page doesn't show it within a limit far longer than any answer takes, and on an error the page's scripts left uncaught). `until` and the errors heard are `pageWatch.ts`'s, an error left uncaught failing `until` as itself even when it times out, shared with `webPage.ts`; the events a field fires as the EM types or leaves it are `fieldEvents.ts`'s. `settled` fails at once while an answer is held, rather than wait on it, and fails on each error the page's scripts left uncaught, as happy-dom reports it on the window: thrown as a script ran, in a listener or in a timer; so does opening the page. An error a script catches is its own to show, and a promise rejection left unhandled fails the run through Vitest. `pagesOnTracker.ts` opens each test's page and closes it, and its app, after; `browserPage.test.ts` tests that the page fails these tests fast and says why. `inputsScript.test.ts` tests the Inputs screen's script (`INPUTS_SCRIPT`): a change saved and noted, the header swapped in with the sections, a refusal swapping in its section alone, a date field saved on leaving it, saves in order, the focus and selection kept, and what is typed while a save is answered, the Connect step left alone, an unchanged form not posted, the server not answering, a chip's dot and Follow, and each save posting its form with the `SAVE_IN_PLACE` header, the page staying where it was. `candidatesScript.test.ts` tests the Comparable work step's candidates script: a link opening a candidate in place, narrowing to a few (`FEW_CANDIDATES` or fewer) opening those once the typing pauses (`NARROWED_DEBOUNCE_MS`) and to more opening none, both read, by the script and the test alike, from the candidates block the page carries them on, typing that goes on opening nothing, an emptied find box opening nothing, and a stale answer ignored. `setupStepScripts.test.ts` tests the Milestone step's find box (`queryStepScript`): the lists narrowed as the EM types, read from what the page's styles display, so a style showing what the script hid fails it, nothing found said, a kind past what was listed asked of the tracker once the typing pauses, an answer older than the latest search dropped, and the list left as it was when the server isn't answering; and that a source chosen at Check (`CHECK_SCRIPT`) posts its form at once, saving the source, and Check opens again showing it chosen. The script submits the form as a browser does, so what the page shows of a refused or failed answer is the browser's: a source the routes refuse is answered not found, and with the server not answering the browser's own page opens, saving nothing either way. happy-dom submits a form as multipart, where a browser sends it urlencoded; `browserPage.ts` reads either for the routes, as the fields are the same.

Each screen's rendering is tested as a component, in `test/app/components/`, with no server started (#236). A component test owns a view rendered: it calls a render function (`renderInputsScreen`, `renderMilestoneForecastScreen`, `renderHowItWorksScreen`, `queryStepSection`, `candidatesHtml`, setup's `setupStepHtml`, `checkStepHtml`, `setupSummaryHtml` and `setupSkippedHtml`, `connectSection`, and `renderPaceTrend`) with a view, built by hand or taken whole from Seam B, arranged through `test/forecast/`'s own helpers (`forecastingForTest` and the scenarios beside it), as Seam B's tests arrange it, rather than copies of them at `test/`'s root, and checks what the page offers the EM: each region, heading, field, button and link by its role and accessible name, the visible text, and where each form posts. It covers the states a view can be in: empty, refused with why, warned, and each source of tickets remaining and pace, with the chip on a typed value the tracker reads differently. What the view says, and when, is Seam B's, so a component test checks no forecast: a date or count it reads is one the view it renders gave, as the screens say it. `test/app/dom.ts` parses the HTML in one happy-dom window with JavaScript off, and queries it by role and name as a screen reader would (`byRole`, `allByRole`, `hasRole`, `accessibleName`), by visible text (`text`, block elements kept apart, what is `hidden` and all but the summary of a closed `<details>` left out), by what a form posts to (`postsTo`), the fields it carries hidden (`hiddenFields`) and a group's radios (`radios`), and by selector where a role and text say too little (`one`, `all`, `around`): a visual state (the headline's emphasis, a bar's height, a shaded week), a block with no role of its own, or what the page carries for its scripts. Its roles (`Role`) are the part of ARIA the screens use. It also reads the Capacity section's state (`capacitySection`) for the route tests of both builds, so `webApp.test.ts` needs no server harness. Its `text` reads a parsed page; `screensHarness.ts`'s `text` strips the tags from a page served over HTTP, for the tests that fetch it. The render functions' files are listed for `app` in `TEST_SEAMS`, as the component layer's entry points. What each screen's page shares, its sidebar marking the screen open, its icon and fonts, and that it loads nothing else, is `htmlPage.test.ts`'s, once for the three screens (`htmlPageHarness.ts`), with the footer's version alone where the build recorded no GitHub repo. `htmlPage.feedback.test.ts` gives the page shell a repo, as `npm run build` records one (#370), by mocking `src/app/feedbackRepo.js`, the one module the tests mock, as the repo is the build's and no view's; it checks each screen's footer reads the version then Send feedback, opening that repo's new-issue form in a new tab, its body naming the version and screen. A screen's arrangement shared by its tests is its `*Harness.ts` (`inputsScreenHarness.ts`, `milestoneForecastScreenHarness.ts`, `htmlPageHarness.ts`), as a `*Scenario.ts` is Seam B's.
