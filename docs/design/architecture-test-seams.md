# Architecture: Test seams

Part of the architecture design; the index is [`architecture.md`](architecture.md).

These docs name each seam and how its tests drive it: the entry point, the harness, what is faked and why. What a test checks lives in the test, so a change to copy, a link or a screen's behaviour edits a seam doc only when it adds, removes or changes a seam.

**Test seams.** There are three:

- **Seam A** is `simulateCase`, tested with fixed seeds ([`engine.md`](engine.md)).
- **Seam B** is `forecast/`, reached through one handle for the team, `Forecasting`, opened on storage (the stored facts and the ledger), a clock, the settings and, in the local server build, what it connects with: each screen's and step's view comes out of it, whole, and each submit is saved or refused with the view to show again. `app/` keeps only reading form fields and query parameters, keeping a candidates opening by its id, and rendering, so refused re-display and each step's behaviour are tested here, without the server, reading through the canned connector and `openMemorySecrets`. The browser build connects nothing, so its views have no Connect or query step. What each view shows is in [`forecast-model.md`](forecast-model.md) and [`frontend-essentials.md`](frontend-essentials.md).

  `app/` reaches it through one handle for the team, `Forecasting`, imported with all it takes and gives from `forecast/index.ts`, the module's one entry point (the rest is private, in `forecast/lib/`), opened once, in `launch.ts` for the server and `webApp.ts` for the browser: `openForecasting({ storage, connecting?, clock, settings? })`. Opening it adds the default team on first launch. The `Clock` is `{ now(), timeZone }`: `now` the UTC instant reads are made at, and `timeZone` the EM's (an IANA name); today is now's calendar date in that time zone, worked out inside `forecast/`, so `app/` builds the clock (`systemClock`) and nothing else of the time. The settings are `DEFAULT_SETTINGS` unless given. Without `connecting` (the browser build) the handle is the same, its views having no Connect or query step; a submit of a step throws, as the browser build sends none. Every method but `connects` is async and takes no team or settings, building each context it needs (`Connecting`, `TrackerReads`, `SetupContext`, `QueryStepping`, and `ReadClock`, the clock read once for the call) from what the handle was opened on, and asking the tracker for the milestone choices once per call. `routes.ts` has one async `route`, which makes at most one handle call per request, and the web app's `show` returns a Promise. Its entry points are the handle's methods (#246):
  - `connects`: whether the handle connects a tracker (the local server build); `app/` answers the setup steps' requests only where it does.
  - `milestoneForecastView(shown?)`: the Milestone forecast screen, its Capacity section open as `shown` asks.
  - `howItWorksView()`: the How it works screen.
  - `inputsScreen(opening?)`: the Inputs screen whole (`InputsScreen`: the inputs; and in the local server build the Connect step, setup, and the query step setup is on), as its URL asks (`InputsOpening`: the step, the query open for editing, the candidates opened, what each find box sent). Only the query step shown is built.
  - `submit(edit, opening?)`: every form, as typed (`Edit`: Inputs, Capacity and pace pattern forms, skips, the Connect step's, setup's own, a query step's, Read again), and what follows from it (`Outcome`, told by its `kind`): `saved`, with the place to go next (`Place`, told by its `kind`: a screen; or on the Inputs screen the setup step, a query step with its query open for editing when it was edited by hand, or the tracker's pace after a skip), which `app/` maps to a path; `savedInPlace` (`inPlace`), with the Inputs screen, its query step asking the tracker nothing; `refused`, with the whole Inputs screen to show again, or `refusedOnForecast`, the Milestone forecast screen, for a form beside the forecast; `refusedThere`, for setup's own forms ("Use these" before the milestone has a query, Cancel once refused), changing nothing, with the place to go to, whose step says why; or `confirmClear`, with the place asking to confirm going back to finding clears a query, its query step open for editing. A save that renames the milestone moves the milestone query to the new name inside `submit`, so `app/` never reads the milestone's name, and says what came of it (`followed`: followed and read, followed but the tracker unread, or refused, the query left as it was).
  - `searchedChoiceList(kind, find, step)`: one kind of a query step's choices searched in the tracker, as its script asks.
  - `openCandidates()`: a candidates opening, which the Comparable work step's script reads more candidates in (`read`).
  - `rerunForecast(log)`: a logged forecast re-run from its case alone, to check it gives the result the EM was shown, or refused as another engine version's.

  `test/forecast/` tests it only through the handle, which each test opens with `forecastingForTest` (`test/forecast/forecastingForTest.ts`, #233), the handle itself with what the test arranges and reads it with: either build's handle on an in-memory SQLite storage, the canned connector answering from a fixture the test can change between reads, `openMemorySecrets` in place of the keychain, and a clock the test can move; it counts what the connector was asked, makes the keychain or the stored connection fail on demand, and restarts the handle on the same storage. The forecast ledger's tests open the browser build's handle through it on a storage of their own (`storedIn`: a SQLite file or browser storage), opened again on each restart, so a restart reads the ledger back from what was written (`forecastLedgerScenario.ts`).

  The handle is built (`lib/forecasting.ts`, `lib/inputsScreenView.ts`, `lib/submit.ts`, each call on what `lib/teamCall.ts` reads the clock and the team into) on the free functions below, private to `forecast/lib/`. `setupView` and `readPicks` have no method, reached through `inputsScreen` and Check's submit:
  - `milestoneForecastView`: the Milestone forecast screen, through the engine.
  - `howItWorksView`: the How it works screen, from the settings.
  - `rerunForecast`: a logged forecast re-run from its case alone, or refused as another engine version's. The ledger goes in through storage; `milestoneForecastView` logs the forecast it shows there.
  - `inputsView`, `submitInputs`: the Inputs screen; a form as typed (`InputsEdit`) saved, saying which screen comes next, or refused, with the screen to show again (Capacity's forms are on the Milestone forecast screen) and its view.
  - These three take the team's tracker reads (`TrackerReads`) in the local server build: its connection and saved reads, which a value following the tracker takes (`measure`), and a typed one is compared with for its chip (`readsDifferently`). With none, or no connection, every value is typed, as in the MVP.
  - `submitSkip`: the tracker's periods skipped or counted again, reading the tracker further back where a skip needs it; saved, or refused with the Inputs screen to show again (`Submitted`, as `submitInputs` gives).
  - `connectionView`, `submitConnection`: the Connect step; a connect checked through a connector, then saved or refused; disconnect.
  - `setupView`, `openSetup`, `submitSetup`: the setup step shown, with Back, Next and Cancel, Check with its rows (the saved values, the draft's readings, and each value's source), or once closed its summary (reading nothing from the tracker) or the inputs typed; `openSetup` picks the step from what the URL asks for or a refused form's, and at Check reads each pick (`readPicks`); a source chosen at Check, held in the draft; "Use these" (applying the setup draft and the sources chosen), Change, Cancel (throwing the draft away and any connection made in the steps, back to how setup was before they opened; refused, with `noCancel` on the view, once they changed the connection they opened on), or skipping connecting; each submit saying the step to open next. They take one `SetupContext`: what a query step reads with, the milestone's inputs, today and the EM's time zone.
  - Each entry point asks storage for the team's queries and reads in a target by name (`teamQueries`), so callers and tests pass the one storage: the setup steps' (`queryStepView`, `submitStepQuery`, `searchedChoiceList`, `openCandidates`, `setupView`, `readPicks`) read and save `current`; the Milestone forecast screen, the Inputs screen's values and setup's summary read `saved`; `submitSkip` and `followRenamedMilestone` change `saved` first, then `current` wherever the steps' own still need it: a draft query of its own, or a read that still falls short. A step's query or Read again, once read, leaves `submit` to read the pace's queries in both targets again where comparable work's read has ended before the reach from today (`reachBack`, #424). Each asks for a target in one way, `withTeamQueries` in `connection.ts`. "Use these" applies the draft through storage (`applySetupDraft`), and Check's choice of source and the picks' failures are saved into the draft through storage too (`saveDraftSources`, `saveDraftPickFailures`).
  - `submitReadAgain`: Read again on the summary, reading nothing while setup is open: the milestone query and comparable work's read again, or, failing, why kept for the summary to say, the saved reads still in use.
  - `queryStepView`: a query step whole, for the query it edits (`StepQuery`): the Milestone step, or the Comparable work step with its pace and its candidates.
  - `searchedChoiceList`: one kind of a query step's choices searched in the tracker, as its script asks.
  - `submitStepQuery`: a query step's submit: its query saved and read, refused, or asking to confirm a clear.
  - `openCandidates`: a candidates opening, which the step's script reads more candidates in (`read`).
  - `followRenamedMilestone`: the milestone query moved to the renamed milestone's, after an Inputs form saves a new name.
  - In v1, `teamFacts`; the MVP has no team facts.

- **Seam C** is the connector interface (`connectors/connector.ts`): a connector built from a connection, a token and a transport goes in, and its milestone choices and reads come out. How each connector is tested there is in [`architecture-test-seams-connectors.md`](architecture-test-seams-connectors.md).

Warning text and provenance are tested at Seam B, not Seam A. These cases moved from the engine tests. Each is owed, in `test/forecast/`, by the ticket that adds its warning or diagnostic. Since the MVP, only the first two can arise: the last four name epics, commits or measured pace, which return after it.

- the horizon warning when fewer trials finish than the highest reported percentile, with the floored percentage and the horizon date, and none when enough finish;
- the long-forecast warning above `warnAboveWeeks` weeks, none at or below it, its ticket figure for 'when' and 'howMany', a median beyond the horizon counting as over, the threshold coming from `ForecastSettings`, and weeks (not periods) keeping their meaning when `periodDays` changes;
- the growth source of each epic in rank order: samples, ambiguity range, or epic size for a null or 0 `baseCount`;
- the throughput scope reported as `'milestoneEpics'`;
- the throughput source: `'measured'` for samples, `'manual'` for a range;
- the uncommitted epics listed in rank order, and none for a scope of committed epics.

Seam B tests read tickets through the canned connector (`connectors/canned.ts`), which returns its fixture's tickets, an empty list for a query that matches nothing, and any failure on cue; `test/connectors/` tests it.

Each test folder imports from `src/` only the files of its seam's entry points and what that seam's tests read through. The one list of those files, by folder, is `TEST_SEAMS` in [`test/testSeams.test.ts`](../../test/testSeams.test.ts), which fails naming any other import; add a file there when a seam gains an entry point. Two kinds of test read through a second seam on purpose, listed file by file as its `ALLOWED_BEYOND_SEAM`: a Seam B test that checks what it shows against Seam A run directly, and a migration test that checks a migrated file by what the forecast reads back from it, through Seam B's views. The imports that still break the rule are its `TEMPORARY_EXCEPTIONS`, each with why it is still there.

Each module's behaviour is covered by its own test folder, not only by tests at an outer layer: CI runs each `test/<folder>/` alone with coverage over its `src/<folder>/` alone (`npm run coverage:folders`, [`scripts/checkOwnFolderCoverage.ts`](../../scripts/checkOwnFolderCoverage.ts)), puts each folder's figures in its summary beside the test and usage coverage, and fails when one drops below that folder's threshold or isn't measured, its tests failing. The thresholds, one set per folder of `src/` that `test/` has a folder for, are `OWN_FOLDER_THRESHOLDS` in [`scripts/ownFolderCoverage.ts`](../../scripts/ownFolderCoverage.ts), the figures as last measured, so any drop fails; raise one when its tests cover more. A folder of `src/` with no test folder of its own (`model/`, types and constants with no logic of their own) is listed there, with why, as `NO_OWN_TEST_FOLDER`.

Tests arrange through the module: test setup calls the module's own functions, never writes its stored data in SQL or opens the database directly, so a change to how a module keeps its data leaves its tests alone; where a test needs a function the module doesn't have, it is added to the module. [`test/arrangeRules.test.ts`](../../test/arrangeRules.test.ts) enforces this across all of `test/`, failing on SQL writes or the database opened directly in any file but the exceptions it lists, each with why: the migration tests, which arrange data as it was before a migration, and the tests of stored data storage can't write, which write it through `test/storage/sqliteStraight.ts` ([`architecture-test-seams-storage.md`](architecture-test-seams-storage.md)).

The tests of `test/app/`, the launch smoke test, the web build's, the browser scripts' and each screen's rendering as a component, are in [`architecture-test-seams-app.md`](architecture-test-seams-app.md). The component tests are not a fourth seam: they test `app/`'s rendering of the views Seam B gives, so the render functions' files are listed for `app` in `TEST_SEAMS` beside its other entry points.

The tests of `scripts/`, the restart, the change-file check and the release among them, are in [`architecture-test-seams-scripts.md`](architecture-test-seams-scripts.md).

The one exception is the PRNG: `engine/random.ts`, kept at `engine/`'s root as a second entry point beside `index.ts` for this alone (the rest of the engine is in `engine/lib/`), is checked against output vectors from the authors' reference C code for xoshiro128**, because a port must reproduce its exact stream and Seam A can't show that.

`test/storage/` holds the Storage contract and the schema migration tests: [`architecture-test-seams-storage.md`](architecture-test-seams-storage.md).
