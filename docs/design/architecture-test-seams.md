# Architecture: Test seams

Part of the architecture design; the index is [`architecture.md`](architecture.md).

**Test seams.** There are three:

- **Seam A** is `simulateCase`, tested with fixed seeds ([`engine.md`](engine.md)).
- **Seam B** is `forecast/`: stored facts, settings and the ledger go in, with what the local server build connects with (`Connecting`, or `QueryStepping` for a query step); each screen's and step's view comes out, whole, and each submit is saved or refused with the view to show again. `app/` keeps only reading form fields and query parameters, keeping a candidates opening by its id, and rendering, so refused re-display and each step's behaviour are tested here, without the server, reading through the canned connector and `openMemorySecrets`. The browser build connects nothing, so its views have no Connect or query step. What each view shows is in [`forecast-model.md`](forecast-model.md) and [`frontend-essentials.md`](frontend-essentials.md).

  `app/` reaches it through one handle for the team, `Forecasting` (`forecast/forecasting.ts`), opened once, in `launch.ts` for the server and `webApp.ts` for the browser: `openForecasting({ storage, connecting?, clock, settings? })`. Opening it adds the default team on first launch. The `Clock` is `{ now(), timeZone }`: `now` the UTC instant reads are made at, and `timeZone` the EM's (an IANA name); today is now's calendar date in that time zone, worked out inside `forecast/`, so `app/` builds the clock (`systemClock`) and nothing else of the time. The settings are `DEFAULT_SETTINGS` unless given. Without `connecting` (the browser build) the handle is the same, its views having no Connect or query step; a submit of a step throws, as the browser build sends none. Every method but `connects` is async and takes no team or settings, building each context it needs (`Connecting`, `TrackerReads`, `SetupContext`, `QueryStepping`, `CandidatesAt`, `SkipAt`) from what the handle was opened on, and asking the tracker for the milestone choices once per call. `routes.ts` has one async `route`, which makes at most one handle call per request, and the web app's `show` returns a Promise. Its entry points are the handle's methods (#246):
  - `connects`: whether the handle connects a tracker (the local server build); `app/` answers the setup steps' requests only where it does.
  - `milestoneForecastView(shown?)`: the Milestone forecast screen, its Capacity section open as `shown` asks.
  - `howItWorksView()`: the How it works screen.
  - `inputsScreen(opening?)`: the Inputs screen whole (`InputsScreen`: the inputs; and in the local server build the Connect step, setup, and the query step setup is on), as its URL asks (`InputsOpening`: the step, the query open for editing, the candidates opened, what each find box sent). Only the query step shown is built.
  - `submit(edit, opening?)`: every form, as typed (`Edit`: Inputs, Capacity and pace pattern forms, skips, the Connect step's, setup's own, a query step's, Read again), and what follows from it (`Outcome`): saved, with the place to go next, and saved in place (`inPlace`) the Inputs screen, its query step asking the tracker nothing; refused, with the whole screen to show again; or asking to confirm going back to finding clears a query. A save that renames the milestone moves the milestone query to the new name inside `submit`, so `app/` never reads the milestone's name.
  - `searchedChoiceList(kind, find, stepQuery)`: one kind of a query step's choices searched in the tracker, as its script asks.
  - `openCandidates()`: a candidates opening, which the Comparable work step's script reads more candidates in (`read`).

  The handle is built (`teamEntries.ts`, `inputsScreenView.ts`, `submit.ts`) on the free functions below, which stay; `test/forecast/` tests them, and #233 ports those tests to the handle. `rerunForecast`, `setupView` and `readPicks` have no method:
  - `milestoneForecastView`: the Milestone forecast screen, through the engine.
  - `howItWorksView`: the How it works screen, from the settings.
  - `rerunForecast`: a logged forecast re-run from its case alone, or refused as another engine version's. The ledger goes in through storage; `milestoneForecastView` logs the forecast it shows there.
  - `inputsView`, `submitInputs`: the Inputs screen; a form as typed (`InputsEdit`) saved, saying which screen comes next, or refused, with the screen to show again (Capacity's forms are on the Milestone forecast screen) and its view.
  - These three take the team's tracker reads (`TrackerReads`) in the local server build: its connection and saved reads, which a value following the tracker takes (`measure`), and a typed one is compared with for its chip (`readsDifferently`). With none, or no connection, every value is typed, as in the MVP.
  - `submitSkip`: the tracker's periods skipped or counted again, reading the tracker further back where a skip needs it; saved, or refused with the Inputs screen to show again (`Submitted`, as `submitInputs` gives).
  - `connectionView`, `submitConnection`: the Connect step; a connect checked through a connector, then saved or refused; disconnect.
  - `setupView`, `openSetup`, `submitSetup`: the setup step shown, with Back, Next and Cancel, Check with its rows (the saved values, the draft's readings, and each value's source), or once closed its summary (reading nothing from the tracker) or the inputs typed; `openSetup` picks the step from what the URL asks for or a refused form's, and at Check reads each pick (`readPicks`); a source chosen at Check, held in the draft; "Use these" (applying the setup draft and the sources chosen), Change, Cancel (throwing the draft away and any connection made in the steps, back to how setup was before they opened; refused, with `noCancel` on the view, once they changed the connection they opened on), or skipping connecting; each submit saying the step to open next. They take one `SetupContext`: what a query step reads with, the milestone's inputs, today and the EM's time zone.
  - Each entry point asks storage for the team's queries and reads in a target by name (`teamQueries`), so callers and tests pass the one storage: the setup steps' (`queryStepView`, `submitStepQuery`, `searchedChoiceList`, `openCandidates`, `setupView`, `readPicks`) read and save `current`; the Milestone forecast screen, the Inputs screen's values and setup's summary read `saved`; `submitSkip` and `followRenamedMilestone` change `saved` first, then `current` wherever the steps' own still need it: a draft query of its own, or a read that still falls short. Each asks for a target in one way, `withTeamQueries` in `connection.ts`. "Use these" applies the draft through storage (`applySetupDraft`), and Check's choice of source and the picks' failures are saved into the draft through storage too (`saveDraftSources`, `saveDraftPickFailures`).
  - `submitReadAgain`: Read again on the summary, reading nothing while setup is open: the milestone query and comparable work's read again, or, failing, why kept for the summary to say, the saved reads still in use.
  - `queryStepView`: a query step whole, for the query it edits (`StepQuery`): the Milestone step, or the Comparable work step with its pace and its candidates.
  - `searchedChoiceList`: one kind of a query step's choices searched in the tracker, as its script asks.
  - `submitStepQuery`: a query step's submit: its query saved and read, refused, or asking to confirm a clear.
  - `openCandidates`: a candidates opening, which the step's script reads more candidates in (`read`).
  - `followRenamedMilestone`: the milestone query moved to the renamed milestone's, after an Inputs form saves a new name.
  - In v1, `teamFacts`; the MVP has no team facts.

- **Seam C** is the connector interface (`connectors/connector.ts`): a connector built from a connection, a token and a transport goes in, and its milestone choices and reads come out. How each connector is tested there is in [`architecture-test-seams-connectors.md`](architecture-test-seams-connectors.md).

Warning text and provenance are tested at Seam B, not Seam A. These cases moved from the engine tests. Each is owed, in `test/forecast/`, by the ticket that adds its warning or diagnostic. Since the MVP, only the first two can arise: the last four name epics, commits or measured pace, which return after it.

- the horizon warning when fewer trials finish than the highest reported percentile, with the floored percentage and the horizon date, and none when enough finish;
- the long-forecast warning above `warnAboveWeeks` weeks, none at or below it, its ticket figure for 'when' and 'howMany', a median beyond the horizon counting as over, the threshold coming from `ForecastSettings`, and weeks (not periods) keeping their meaning when `periodDays` changes;
- the growth source of each epic in rank order: samples, ambiguity range, or epic size for a null or 0 `baseCount`;
- the throughput scope reported as `'milestoneEpics'`;
- the throughput source: `'measured'` for samples, `'manual'` for a range;
- the uncommitted epics listed in rank order, and none for a scope of committed epics.

Seam B tests read tickets through the canned connector (`connectors/canned.ts`), which returns its fixture's tickets, an empty list for a query that matches nothing, and any failure on cue; `test/connectors/` tests it.

Each test folder imports from `src/` only the files of its seam's entry points and what that seam's tests read through. The one list of those files, by folder, is `TEST_SEAMS` in [`test/testSeams.test.ts`](../../test/testSeams.test.ts), which fails naming any other import; add a file there when a seam gains an entry point. Two kinds of test read through a second seam on purpose, listed file by file as its `ALLOWED_BEYOND_SEAM`: a Seam B test that checks what it shows against Seam A run directly, and a migration test that checks a migrated file by what the forecast reads back from it, through Seam B's views. The imports that still break the rule are its `TEMPORARY_EXCEPTIONS`, each with why it is still there.

Each module's behaviour is covered by its own test folder, not only by tests at an outer layer: CI runs each `test/<folder>/` alone with coverage over its `src/<folder>/` alone (`npm run coverage:folders`, [`scripts/checkOwnFolderCoverage.ts`](../../scripts/checkOwnFolderCoverage.ts)), puts each folder's figures in its summary beside the test and usage coverage, and fails when one drops below that folder's threshold or isn't measured, its tests failing. The thresholds, one set per folder of `src/` that `test/` has a folder for, are `OWN_FOLDER_THRESHOLDS` in [`scripts/ownFolderCoverage.ts`](../../scripts/ownFolderCoverage.ts), the figures as #262 measured them, so any drop fails; raise one when its tests cover more. A folder of `src/` with no test folder of its own (`model/`, types and constants with no logic of their own) is listed there, with why, as `NO_OWN_TEST_FOLDER`.

Tests arrange through the module: test setup calls the module's own functions, never writes its stored data in SQL or opens the database directly, so a change to how a module keeps its data leaves its tests alone; where a test needs a function the module doesn't have, it is added to the module. [`test/arrangeRules.test.ts`](../../test/arrangeRules.test.ts) enforces this across all of `test/`, failing on SQL writes or the database opened directly in any file but the exceptions it lists, each with why: the migration tests, which arrange data as it was before a migration, and the tests of stored data storage can't write, which write it through `test/storage/sqliteStraight.ts` ([`architecture-test-seams-storage.md`](architecture-test-seams-storage.md)).

`test/app/` holds the launch smoke test. It is not a forecasting seam: it builds the app, runs the built `npm start` entry point (`dist/app/main.js`) with `FORECASTER_NO_BROWSER=1` so no browser opens and a temporary `FORECASTER_DATA_FILE`, and checks that the Milestone forecast screen is served in its empty state, with no sample data. It runs it again in demo mode (`FORECASTER_DEMO=1`), on the canned connector built from the synthetic fixture, so no token is needed, and checks the screen is served. It also checks that a bad `PORT` is refused. `test/app/launch.test.ts` starts the server in-process, on port 0, and checks that it refuses a request whose `Host`, or a POST whose `Origin`, isn't its own, with no route run, sending a foreign `Host` through `node:http` because `fetch` sets its own.

The tests of `scripts/`, the restart, the change-file check and the release among them, are in [`architecture-test-seams-scripts.md`](architecture-test-seams-scripts.md).

The web build is tested the same way, with no seam of its own: `webApp.test.ts` asks its app for screens as its page does, and the web build smoke test runs `npm run build:web` and checks the one page it writes opens on the empty state with its script inline. The smoke test also runs that script, as bundled, in Node on a stub of the browser parts it opens with, and posts a milestone and pace through the `fetch` it answers for the Inputs screen's saves, so what the bundling breaks in the app fails a test (#280). Its page script's (`webMain.ts`) wiring of links and forms in a real browser is checked by the browser check (`npm run check:browser`, a CI job of its own), which drives the local app and the web build in Chrome from empty to a forecast, and by the ticket's demo, not by tests.

The Inputs screen's browser scripts are tested in `test/app/` too, in [happy-dom](https://github.com/capricorn86/happy-dom), so no browser is installed, locally or in CI (#275). `test/app/browserPage.ts` opens a page of `appOnTracker`'s running app at its URL, with JavaScript on in that helper alone, as it opens only the app's own pages, and the `/live` reload script's `EventSource` stubbed so tests end. The page's scripts run as the browser runs them, and their `fetch` reaches the real server, the canned connector and the storage in memory, with nothing faked. A test changes a field and fires its event, waits for the page to settle (`settled`, which waits out each request and timer, the candidates' debounce among them), then checks the page and what storage now holds; to make answers arrive out of order, it holds one back (`holdAnswer`), and waits on what the page shows meanwhile (`until`, which fails, saying what it waited for, if the page doesn't show it within a limit far longer than any answer takes). `settled` fails at once while an answer is held, rather than wait on it, and fails on each error the page's scripts left uncaught, as happy-dom reports it on the window: thrown as a script ran, in a listener or in a timer; so does opening the page. An error a script catches is its own to show, and a promise rejection left unhandled fails the run through Vitest. `pagesOnTracker.ts` opens each test's page and closes it, and its app, after; `browserPage.test.ts` tests that the page fails these tests fast and says why. `inputsScript.test.ts` tests the Inputs screen's script (`INPUTS_SCRIPT`): a change saved and noted, the header swapped in with the sections, a refusal swapping in its section alone, a date field saved on leaving it, saves in order, the focus and selection kept, and what is typed while a save is answered, the Connect step left alone, an unchanged form not posted, the server not answering, and a chip's dot and Follow. `candidatesScript.test.ts` tests the Comparable work step's candidates script: a link opening a candidate in place, narrowing to a few (`FEW_CANDIDATES` or fewer) opening those once the typing pauses (`NARROWED_DEBOUNCE_MS`) and to more opening none, both read, by the script and the test alike, from the candidates block the page carries them on, typing that goes on opening nothing, an emptied find box opening nothing, and a stale answer ignored. `setupStepScripts.test.ts` tests the Milestone step's find box (`queryStepScript`): the lists narrowed as the EM types, read from what the page's styles display, so a style showing what the script hid fails it, nothing found said, and a kind past what was listed asked of the tracker once the typing pauses; and that a source chosen at Check (`CHECK_SCRIPT`) posts at once. happy-dom submits a form as multipart, which the server doesn't read, so what that post saves stays tested over HTTP.

The one exception is the PRNG: `engine/random.ts`, kept at `engine/`'s root as a second entry point beside `index.ts` for this alone (the rest of the engine is in `engine/lib/`), is checked against output vectors from the authors' reference C code for xoshiro128**, because a port must reproduce its exact stream and Seam A can't show that.

`test/storage/` holds the Storage contract and the schema migration tests: [`architecture-test-seams-storage.md`](architecture-test-seams-storage.md).
