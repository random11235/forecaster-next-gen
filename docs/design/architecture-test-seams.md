# Architecture: Test seams

Part of the architecture design; the index is [`architecture.md`](architecture.md).

**Test seams.** There are three:

- **Seam A** is `simulateCase`, tested with fixed seeds ([`engine.md`](engine.md)).
- **Seam B** is `forecast/`: stored facts, settings and the ledger go in, with what the local server build connects with (`Connecting`, or `QueryStepping` for a query step); each screen's and step's view comes out, whole, and each submit is saved or refused with the view to show again. `app/` keeps only reading form fields and query parameters, keeping a candidates opening by its id, and rendering, so refused re-display and each step's behaviour are tested here, without the server, reading through the canned connector and `openMemorySecrets`. The browser build connects nothing, so its views have no Connect or query step. What each view shows is in [`forecast-model.md`](forecast-model.md) and [`frontend-essentials.md`](frontend-essentials.md). Its entry points:
  - `milestoneForecastView`: the Milestone forecast screen, through the engine.
  - `howItWorksView`: the How it works screen, from the settings.
  - `inputsView`, `submitInputs`: the Inputs screen; a form as typed (`InputsEdit`) saved, saying which screen comes next, or refused, with the screen to show again (Capacity's forms are on the Milestone forecast screen) and its view.
  - These three take the team's tracker reads (`TrackerReads`) in the local server build: its connection and saved reads, which a value following the tracker takes (`measure`), and a typed one is compared with for its chip (`readsDifferently`). With none, or no connection, every value is typed, as in the MVP.
  - `submitSkip`: the tracker's periods skipped or counted again, reading the tracker further back where a skip needs it; saved, or refused with the Inputs screen to show again (`Submitted`, as `submitInputs` gives).
  - `connectionView`, `submitConnection`: the Connect step; a connect checked through a connector, then saved or refused; disconnect.
  - `setupView`, `openSetup`, `submitSetup`: the setup step shown, with Back, Next and Cancel, Check with its rows (the saved values, the draft's readings, and each value's source), or once closed its summary (reading nothing from the tracker) or the inputs typed; `openSetup` picks the step from what the URL asks for or a refused form's, and at Check reads each pick (`readPicks`); a source chosen at Check, held in the draft; "Use these" (applying the setup draft and the sources chosen), Change, Cancel (throwing the draft away and any connection made in the steps, back to how setup was before they opened; refused, with `noCancel` on the view, once they changed the connection they opened on), or skipping connecting; each submit saying the step to open next. They take one `SetupContext`: what a query step reads with, the milestone's inputs, today and the EM's time zone.
  - Each entry point asks storage for the team's queries and reads in a target by name (`teamQueries`), so callers and tests pass the one storage: the setup steps' (`queryStepView`, `submitStepQuery`, `searchedChoiceList`, `openCandidates`, `setupView`, `readPicks`) read and save `current`; the Milestone forecast screen, the Inputs screen's values and setup's summary read `saved`; `submitSkip` and `followRenamedMilestone` change `saved` first, then `current` wherever the steps' own still need it: a draft query of its own, or a read that still falls short. Each asks for a target in one way, `withTeamQueries` in `connection.ts`. "Use these" applies the draft through storage (`applySetupDraft`), and Check's choice of source and the picks' failures are saved into the draft through storage too (`saveDraftSources`, `saveDraftPickFailures`).
  - `submitReadAgain`: Read again on the summary, reading nothing while setup is open: the milestone query and comparable work's read again, or, failing, why kept for the summary to say, the saved reads still in use.
  - `queryStepView`: a query step whole, for the query it edits (`StepQuery`): the Milestone step, or the Comparable work step with its pace and its candidates.
  - `searchedChoiceList`: one kind of a query step's choices searched in the tracker, as its script asks.
  - `submitStepQuery`: a query step's submit: its query saved and read, refused, or asking to confirm a clear.
  - `openCandidates`: a candidates opening, which the step's script reads more candidates in (`read`).
  - `followRenamedMilestone`: the milestone query moved to the renamed milestone's, after an Inputs form saves a new name.
  - In v1, `teamFacts`; the MVP has no team facts.
- **Seam C** is the connector interface (`connectors/connector.ts`): a connector built from a connection, a token and a transport goes in, and its milestone choices and reads come out. See [Seam C](#seam-c-connectors) below.

Warning text and provenance are tested at Seam B, not Seam A. These cases moved from the engine tests. Each is owed, in `test/forecast/`, by the ticket that adds its warning or diagnostic. Since the MVP, only the first two can arise: the last four name epics, commits or measured pace, which return after it.

- the horizon warning when fewer trials finish than the highest reported percentile, with the floored percentage and the horizon date, and none when enough finish;
- the long-forecast warning above `warnAboveWeeks` weeks, none at or below it, its ticket figure for 'when' and 'howMany', a median beyond the horizon counting as over, the threshold coming from `ForecastSettings`, and weeks (not periods) keeping their meaning when `periodDays` changes;
- the growth source of each epic in rank order: samples, ambiguity range, or epic size for a null or 0 `baseCount`;
- the throughput scope reported as `'milestoneEpics'`;
- the throughput source: `'measured'` for samples, `'manual'` for a range;
- the uncommitted epics listed in rank order, and none for a scope of committed epics.

Seam B tests read tickets through the canned connector (`connectors/canned.ts`), which returns its fixture's tickets, an empty list for a query that matches nothing, and any failure on cue; `test/connectors/` tests it.

Each test folder imports from `src/` only the files of its seam's entry points and what that seam's tests read through. The one list of those files, by folder, is `TEST_SEAMS` in [`test/testSeams.test.ts`](../../test/testSeams.test.ts), which fails naming any other import; add a file there when a seam gains an entry point. Two kinds of test read through a second seam on purpose, listed file by file as its `ALLOWED_BEYOND_SEAM`: a Seam B test that checks what it shows against Seam A run directly, and a migration test that checks a migrated file by what the forecast reads back from it, through Seam B's views. The imports that still break the rule are its `TEMPORARY_EXCEPTIONS`, each with why it is still there.

### Seam C: connectors

Each real connector is tested at Seam C, offline, on raw responses recorded from the synthetic trackers and replayed through its injected transport.

A rate limit (a 429, or a GitHub 403 whose headers say it is one; on Jira only a 429) is backed off inside the connector, by the backoff both share beside `send` (`connectors/remote.ts`): the request is sent again up to three times, after the wait the tracker asks for (its `retry-after`, or, for GitHub's primary rate limit, until its `x-ratelimit-reset`), else 1, 2 and 4 seconds. Still rate limited after that, or asked to wait more than a minute, the call fails as `unavailable`. No other failure is sent again. Each connector takes how it waits as an optional last argument (`Wait`, a timer by default), so the suite backs off without waiting out real delays: its `rateLimited` subject puts a tracker answering 429s in front of the replay.

- **The contract suite** (`test/connectors/connectorContract.test.ts`), modelled on the Storage contract, runs the same cases against every connector: a read returning tickets, a query matching nothing (an empty list, not a failure), each failure, milestone choices returning choices or a failure, a search of each kind's choices finding the same choice the milestone choices list (or nothing, or a failure), and a picked nested epic read to every leaf beneath it, its sub-epics found by the read rather than kept in the query. Each connector joins it with a `ContractSubject` (`connectorContract.ts`): its connector on the synthetic tracker, with a refused token, on an unknown repo or project, with no network (its transport rejects with the `TypeError` `fetch` does), and replaying no recordings, plus its queries in the tracker's syntax, its tickets' ids by role, and the roles its hierarchy cases read. A tracker whose search caps its results (GitHub's, at 1,000) also gives a connector on a search finding more than the cap; the synthetic repo is too small to reach it, so that one stands in for GitHub rather than replaying it. A connector maps only a network failure to `unavailable`, so on a request with no recording the replay's error propagates and the case fails loudly; the suite checks this for each connector. Later specs add their cases to this suite. Tracker-only quirks are tested beside it, in the tracker's own folder (`test/connectors/github/`, `test/connectors/jira/`).
- **The replay transport** (`test/connectors/replayTransport.ts`) answers each request with the recording of the same method, URL and body, and throws, naming the request, when there is none, so a missing recording never passes silently.
- **Recordings** come only from the synthetic trackers (`random11235/forecaster-synthetic` for GitHub, the space `SYN` on `ralphhockley.atlassian.net` for Jira), which `scripts/synthetic/` seeds; its manifests map each case's role to its ticket. Failures are real recorded responses where the tracker gives one: a refused token is recorded with a token the tracker refuses, an unknown repo or project with one that doesn't exist. Only the network failing is not recorded. Recordings keep each response's status and only the fields the connector reads, and no headers.
- **The scenarios** (`test/connectors/scenarios.ts`) name, for each tracker, what is recorded: the synthetic connection, the unknown one, and the choices searched for and queries read in each scenario, among them the tracker's own quirks (such as GitHub's short-form `parent-issue:#106`, which matches nothing). The contract suite replays them and the recording script records them, so the two can't drift.
- **The recording script** (`scripts/record.ts`: `npm run record` for both trackers, `npm run record:github` or `npm run record:jira` for one) reads its tokens from the macOS Keychain (`forecaster-github-recording`, `forecaster-jira-recording`) and records Jira as the shared test account `forecastertest3@gmail.com` (`FORECASTER_JIRA_EMAIL` overrides it), never writing a token anywhere, runs each connector's own requests against its synthetic tracker, searching its choices and reading each query both from the start (`FROM_THE_START`) and from the manifest's `cut`, the two `finishedSince`s the contract cases read from, and rewrites `test/connectors/<tracker>/recordings/`. It says plainly when a tracker refuses its token: GitHub's expires on 2026-12-07, Jira's after 30 days. A change to a connector's requests needs a re-run: the replay transport names any request left unrecorded. Node runs the script directly, so the files it imports from `src/` and `test/` (`connectors/remote.ts`, `recording.ts`, `scenarios.ts`), named by their `.ts`, must import nothing at runtime themselves; `test/connectors/recordScript.test.ts` checks that it loads. It loads the connectors from the build in `dist/`.
  `test/app/` holds the launch smoke test. It is not a forecasting seam: it builds the app, runs the built `npm start` entry point (`dist/app/main.js`) with `FORECASTER_NO_BROWSER=1` so no browser opens and a temporary `FORECASTER_DATA_FILE`, and checks that the Milestone forecast screen is served in its empty state, with no sample data. It runs it again in demo mode (`FORECASTER_DEMO=1`), on the canned connector built from the synthetic fixture, so no token is needed, and checks the screen is served. It also checks that a bad `PORT` is refused. `test/app/launch.test.ts` starts the server in-process, on port 0, and checks that it refuses a request whose `Host`, or a POST whose `Origin`, isn't its own, with no route run, sending a foreign `Host` through `node:http` because `fetch` sets its own.
  `test/scripts/restartLocal.test.ts` is not a forecasting seam either: it runs `scripts/restartLocal.sh`, which the restart workflow (`.github/workflows/restart-local.yml`) calls after each merge to `main`, against the same built app on a spare `PORT`, with a stand-in `open` on `PATH`, writing the app's launch agent to its own directory (`LAUNCH_AGENTS_DIR`). It checks that the script stops what held the port and leaves the app serving after it exits, run by launchd as a launch agent in the user's login session, where it can read the keychain (#290), fails with the app's output when the app doesn't come up, and opens a tab only when no page reconnects to `/live`. The script runs only on macOS, as the runner does, so the test skips on CI's Linux and runs in the pre-push hook. The workflow and the runner setup wizard (`scripts/setupRunner.sh`) are checked by a real merge, not by tests. `test/scripts/changeFiles.test.ts` tests the change-file check `check:static` runs on a branch (`changeFileProblems` in `scripts/changeFiles.ts`), on a branch's files at its base and head, and where a release's section goes in `CHANGELOG.md`. `test/scripts/mergeBase.test.ts` tests how those checks find the commit they diff from (`scripts/mergeBase.ts`): a base's merge-base with HEAD, and a base the repo doesn't have failing with the caller's hint for getting it. The release ([`architecture.md`](architecture.md#release)), `scripts/release.ts`, is tested in git repos of its own, never the real repo's, with the tags, branches and merges each case needs (`test/scripts/releaseRepo.ts`): `test/scripts/release.test.ts` the version and section the change files make and which change files a release takes, with each one's PR; `test/scripts/release.run.test.ts` runs the script as the release job does, from a clone of a bare repo standing in for GitHub: merges released in turn and in flight together, a change file a red run left, a docs-only merge, an app change with no change file, and a push refused, then retried or given up. The job itself is checked by a real merge. `test/scripts/prePush.test.ts` runs the pre-push hook (`.husky/pre-push`) in a stand-in clone whose `npm run check` passes or fails, and checks that a failing one refuses the push with its output shown.

The web build is tested the same way, with no seam of its own: `webApp.test.ts` asks its app for screens as its page does, and the web build smoke test runs `npm run build:web` and checks the one page it writes opens on the empty state with its script inline. The smoke test also runs that script, as bundled, in Node on a stub of the browser parts it opens with, and posts a milestone and pace through the `fetch` it answers for the Inputs screen's saves, so what the bundling breaks in the app fails a test (#280). Its page script's (`webMain.ts`) wiring of links and forms in a real browser is checked by the browser check (`npm run check:browser`, a CI job of its own), which drives the local app and the web build in Chrome from empty to a forecast, and by the ticket's demo, not by tests.

The one exception is the PRNG: `engine/random.ts` is checked against output vectors from the authors' reference C code for xoshiro128**, because a port must reproduce its exact stream and Seam A can't show that.

`test/storage/` holds the Storage contract, one suite run against both the SQLite file and the web build's browser storage, and the schema migration tests. The team's connection, the last read of each query, the milestone's picks and query, and its setup: where it stands (`setups`: open or closed, how, and what the steps did to the connection), its draft (`setup_drafts` with its reads, their tickets and its picks' failures in rows of their own) and why its last reads failed (`read_failures`, by what failed: whole, a query's, or a pick's) (`ConnectionStorage`, `SavedReadStorage`, `MilestoneQueryStorage` and `SetupStorage`, part of `openSqliteStorage`'s `SqliteStorage`) are kept only by the SQLite file, so their cases run against SQLite alone: the browser build has no connectors. The team's queries and reads come in two targets (`TeamQueryStorage.teamQueries`): `current`, the setup draft over what's saved while setup is open, otherwise what's saved, which the setup steps read and save; and `saved`, what's saved only, which the forecast reads. Applying the draft ("Use these", `TeamQueryStorage.applySetupDraft`), discarding it (Cancel, `discardSetupDraft`), and saving its sources and picks' failures (`saveDraftSources`, `saveDraftPickFailures`) are storage operations. The setup draft over what's saved is plain TypeScript in `src/storage/lib/setupDraft.ts`, behind `sqliteStorage.ts`, tested only through the contract: its cases cover each target with setup open and closed, applying the draft and discarding it. The migration tests are not a forecasting seam either: they write a data file as an earlier release left it, open it through `openSqliteStorage`, and check what reads back, through storage or through Seam B's views. A branch into main that changes the schema appends at most one step to `MIGRATIONS` in `src/storage/sqliteStorage.ts`, never editing a released one, and adds a test there that opens a file from the version before. Tickets on an integration branch extend that branch's one unreleased step rather than appending their own. `npm run check:migrations` (part of `npm run check`, so of the pre-push hook and CI) checks both rules against main. The values of every union that reaches storage are frozen by a snapshot, `test/storage/storedValues.snapshot`. `storedUnions.ts` lists the unions, each with the columns that store it, bound to their types by the typecheck, which also fails on a union a storage's `save…` method takes that isn't listed. A union `sqliteStorage.ts` writes that no `save…` method takes (`read_failures.of`) is typed in `storedUnions.ts`'s `SqliteEncodings` instead, and the typecheck can't tie it to the literals the file writes: `storageContract.storedValues.test.ts` checks the file writes exactly its listed values, and reads back every listed value of each union it reads by a list of its own (how setup was closed, what an opening did to the connection, a read's failure, a drafted source). `storedValues.test.ts` fails on a listed union the snapshot doesn't hold as listed, and on a value in the snapshot at the merge-base with released main (`MAIN_REF`, origin/main, as the migration check; never `CHECK_BASE`, since only released values can be in saved data) that a column no longer stores, unless a migration step on the branch maps it in that column (its statements on the column name it, quoted, more often than the base's do) and, for a union the web build's storage keeps, `webStorage.ts` still names it in its code, to map it as it reads. A union only renamed, its values stored where they were, needs no migration. Two limits are known: the web build's storage has no columns, and its code naming a value at all counts as mapping it, for every union that has it, even where it names the value for another reason; and a statement is on a column when it names the table and the column anywhere, in a subquery too.
