# Forecast model: reads of the team's queries (#158)

Part of the forecast model design; the index is [`forecast-model.md`](forecast-model.md), which has the rest of the settings, pace among them.

The milestone query and comparable work's are each read through `readQuery`, as far back as `finishedSinceFor` reaches, which saves the read (`SavedReadStorage`) or, failing, leaves the saved one in place. `finishedPerPeriod` buckets a read's finishes into periods, each on its calendar day in the EM's time zone, and `ticketsRemaining` counts its open tickets. With several picks, comparable work's read also reads each pick once, for its chip's strip and how many only it brings in; the milestone query's picks are not read one by one.

`paceReads` gives both saved reads per period side by side, over the whole periods both reach, and says which one pace comes from: comparable work's alone once its query is added and finished something in those periods, else the milestone's own over the periods since its start date. An incomplete read isn't counted, so a capped milestone read leaves its own counts and tickets remaining unknown, but not a pace from comparable work. Each ticket counts once by id, and tickets remaining come from the milestone query alone. With a connection, tickets remaining has a source (`ticketsSource`): typed, or following the tracker, when it is the milestone query's latest read's open tickets, updated by each read without asking; an incomplete or missing read gives no forecast until the query is read whole or a number is typed. Typing a number switches it to typed; the typed number is kept while it follows. With no connection it is typed, its source kept for when the team reconnects. The Comparable work step's pace (`comparableWorkPace`) comes from those saved reads, asking the tracker nothing.

With a connection, pace can follow the tracker too (`paceMode` `tracker`, #212), beside typed counts and the range, each kept while another is used. Its window (`trackerWindow`, on `paceReads`' pace) is up to the 8 most recent whole periods not skipped, at the milestone's cadence (amending #133's "the 8 most recent whole periods"): the current period is left out, and quiet periods count 0. It holds as many as the tracker has, bounded by the saved read's reach (`finishedSince`), and leaves out the quiet periods before the first with a ticket finished in either read, the milestone's or comparable work's, whichever pace comes from; quiet periods after it count 0. With pace from comparable work whose latest read has no open tickets, such as a closed epic, the window ends at the period of its last finished ticket, leaving out those after: they don't mean the team is slow, as nothing comparable was left to finish (#411). With any ticket open in it, the quiet periods after its last finish still count 0, as the team may have stalled on it; the milestone's own pace always runs up to the current period. Its line says what bounds it: "last 8 weeks"; "7 weeks · the read reaches back to w/c 14 Sep" when the reads run out first, naming the read's reach, not the tracker's history, which may hold more (#415); "From the first finished ticket, 3 Nov." with leading quiet periods left out (the date is that period's start). Ended at finished comparable work, a line says so, "To the last finished ticket, 15 Nov: comparable work has no open tickets." (the date is that ticket's own), on the Inputs screen and beside the forecast, whose pace line then drops "last": "GitHub's 3 weeks". A young repo, whose early periods come back empty because nothing existed to finish, can't be told from a quiet start by its finished tickets alone, so it shows the same "From the first finished ticket" line, with no signal of its own (#159 review). The reach line is for a read that reaches back less far than the window: one a skip's or a cadence change's reach-back read failed to widen ("4 sprints · the read reaches back to the sprint of 14 Sep"). A skip, and a cadence saved, read the pace's queries again as far back as the window then needs, where their reads fall short (`reachBack`, #213, #415). Short of the 4 a forecast needs, its problem offers Read again, which reads as far back as the window needs, before typing counts or the range; not when the window ends at finished comparable work, which no read lengthens. With the milestone's own pace the window starts at the start date, and the line says "5 weeks · since the start date". With none finished since it, as with a start date of today, before a week since it has ended, the line and problem say so and how many the tracker finished before it, which don't count, rather than that the tracker has none: "no week since the start date has ended · GitHub finished 44 before it" (#405). A line beneath names the current period and what it finished so far. A period ending after the read isn't whole, so the window ends before the read's period, and the line says which periods wait for a read (#390). `assessMilestone` treats its counts as it does typed counts, needing 4 for a forecast and 8 to be reliable; the forecast's pace line names it, "GitHub's last 8 weeks". The pace action, trend and pattern read its counts as they read typed counts. Typing into its periods, opened on the Inputs screen, switches pace to typed counts, starting from its counts. With no connection, a pace following the tracker uses the typed counts. With no pace because a read it would come from is incomplete, pace is marked incomplete beside it, and there is no forecast from it. The read reaches back 8 whole periods at the milestone's cadence, plus one for the current period and one for each period skipped (`finishedSinceFor`, #213), and each saved read keeps how far it reached.

The EM can skip a tracker period that says nothing about the pace ahead (a holiday, say), from its block on the Inputs screen (`submitSkip`, #213). Skips belong to the milestone (`paceWindow.skippedPeriods`, by each period's start date), so they outlast reads. The window passes over them and reaches back to keep up to 8 counted; a skip re-reads the pace's queries, the milestone's and comparable work's, whose saved reads don't reach that far, and counting a period again reads nothing. The bars show a skipped period as a gap, its block struck through with a button to count it again, and a line says which and what counts instead: "2 skipped (12 Oct, 19 Oct), reaching back to w/c 31 Aug"; "…, and GitHub has no earlier weeks to count instead" short of 8. The forecast's pace line adds them, "GitHub's last 8 weeks, 2 skipped". With every period skipped there is no pace and no forecast: "Every week is skipped, so GitHub gives no pace. Count a week again, or use typed counts or the range." With every one that finished something skipped, but quiet ones before them not, the same, saying "Every week that finished something is skipped". Comparable work's pace (`comparableWorkPace`) still counts the periods it reads, skipped or not.

A value following the tracker shows, faintly, the value its latest read replaced (#214): "was 34 on 28 Oct 09:05". Each query's read keeps the read it replaced (`previousRead`), so the previous tickets remaining is that read's open tickets, and the previous pace is the counts pace showed from it, on the day it was made, with the other query's read as it is. None before a second read, while the value is typed, nor when the read changed nothing: the previous counts equal those shown, or those the latest read gives on its own day.

A candidate for comparable work (`openCandidates`) is read the same way, kept only by its opening, and its periods laid on the milestone's cadence from its start date (from today before it has one). It is compared with the milestone's own by one rule (`paceVersusMilestoneOwn`): within 0.5 a period is about the same.

Both screens' views take the same `ForecastSettings` and judge the milestone by one assessment (`assessMilestone`), so the typed counts a forecast needs, the notes beside the inputs and the Inputs screen's hint all come from those settings.
